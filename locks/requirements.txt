# harness/locks/requirements.txt
#
# Named requirements.txt, and living in its own directory, because that is
# the only filename trivy's pip analyzer recognises. Named .lock it parsed as
# nothing and the instrument reported zero results over a file it could not
# read, which is a worse failure than the absent scanner it replaced: a clean
# result and an unreadable subject are indistinguishable downstream. The
# developer-facing harness/requirements.txt is untouched and still declares
# intent with floating bounds.
#
# Resolved versions for the harness Python surface, generated from the
# harness/.venv interpreter that actually runs it.
#
# requirements.txt declares every dependency with a floating lower bound
# (aiohttp>=3.9, pandas>=2.0, ...) and carried no lockfile. A range does
# not resolve to a version, so a vulnerability database has nothing to
# match against and the dependency scanner reported on what it could
# resolve rather than failing: C-GAP-FLOATING-PYTHON-SPECS-UNRESOLVABLE.
# This file gives it something to match.
#
# Generated, not hand-maintained. requirements.txt stays the declaration
# of intent; this is the resolution of it at a point in time. Regenerate
# when the venv is rebuilt, and treat a diff here as a tracked input
# delta rather than noise.
#
# NOT covered: harness/services/cc-bridge/requirements.txt, which carries
# four floating specs (fastapi, uvicorn, anthropic, httpx) and has no
# environment on this host to resolve against. That half of the gap
# stands.
